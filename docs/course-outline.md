# Course: Build your team's PX reviewer

The PX Review source code is free and MIT licensed. The course is optional:
teams pay for a guided path, working sessions, calibration practice, and a finished
deployment—not for permission to use the code.

## Who it is for

DesignOps and design-system leads working with a developer or GitHub administrator;
frontend platform teams; and product-design leaders who want review standards to
operate in the pull-request workflow.

## Outcome

Each team leaves with an organization-owned GitHub App, a deployed review worker,
product-specific policy and context, a calibration set, and an operating agreement
for what the reviewer may block.

## Curriculum

1. **Define reviewable product experience**  
   Use the eight-category PX taxonomy, separate evidence from judgment, and decide
   what a pull request can and cannot prove.

2. **Teach the reviewer your product**  
   Map briefs, components, tokens, content guidance, interaction conventions, and
   repository structure into bounded review context.

3. **Design the review contract**  
   Set severity, confidence, coverage, line placement, noise limits, and rules for
   `not evaluated`.

4. **Deploy an organization-owned GitHub App**  
   Configure least-privilege permissions, webhook verification, secrets, the model
   provider, and a production deployment inside the team's environment.

5. **Calibrate on real pull requests**  
   Measure useful findings, false positives, misses, duplicates, and reviewer
   disagreement. Tune context and thresholds before enforcement.

6. **Govern and evolve the reviewer**  
   Establish policy ownership, release and rollback practices, dependency updates,
   provider/data-retention review, and a safe path for taxonomy changes.

## Suggested capstone

Run PX Review in advisory mode on 10–20 representative pull requests. Present the
calibration evidence, make one deliberate policy change, and enable a required check
only for the severity level the evidence supports.
